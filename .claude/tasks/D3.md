# D3 — JSON material config: data-driven material definition

## Goal
Enable material parameters (feature set, textures, colors, scalar uniforms) to be specified in JSON files and loaded at startup via a `MaterialLoader`, so tweaks to pilot materials no longer require C++ recompilation.

## Context

**Engine/game boundary.** The `MaterialBuilder` / `MaterialInstance` / `IMaterialFeature` stack lives in `snake3d_engine` (`Renderer/Opengl/Material/`). JSON loading glue is also engine territory. Pilot callsites being migrated are in `snake3d_game` (game layer: `Scenes/` and `Renderer/Opengl/Model/Game/`).

**Existing JSON infrastructure.** `nlohmann_json` is already a public dependency of `snake3d_engine` (CMakeLists.txt line 456). The pattern for loading a JSON manifest and driving resource creation already exists in `App.cpp::loadAssets` (reads `Assets/texture_manifest.json` with `nlohmann::json`). That is the direct analogous implementation for D3's loader.

**Material construction today.** Every pilot material uses the `MaterialBuilder` fluent API:
```
MaterialBuilder().useMaster("basicShader").with(featureA).with(featureB).build(*registry)
```
Each call to `with(...)` adds an `IMaterialFeature` subclass. Features that only need static data (color, intensity, texture path, scalar) can be fully round-tripped through JSON. Features that need live C++ objects (lighting pointers, `ShadowFeature` holding a `TextureManager` for the depth array, `FogFeature` shared singleton) are **runtime-wired** after JSON load — the JSON spec records their presence, and the callsite provides the live objects to a post-load hook.

**Pilot materials (3 materials, lowest C++ coupling):**

1. **Snake tile** (`SnakeMeshNode3D.cpp` lines 59-68): pure color red (`{0.88, 0.05, 0.05}`), `LightingFeature` (empty lights initially, updated via setters), `ShadowFeature`, `FogFeature`. No textures.
2. **Barrel** (`BarrelNode3D.cpp` lines 23-36): `LightingFeature`, `ShadowFeature`, `NormalMapFeature` (texture loaded lazily), `AlbedoFeature` (texture loaded lazily), `FogFeature`. `ambientIntensity=2.5`.
3. **Torch** (`TorchScene.cpp` lines 82-91): `LightingFeature` (directional + spotLights, no points), `ShadowFeature`, `NormalMapFeature("torch_normal.png")`, `AlbedoFeature("torch.png")`, `FogFeature`. Fully static textures from ResourceManager keys.

**Key constraints:**
- Features holding live runtime pointers (`LightingFeature` lights, `ShadowFeature` depth texture, `FogFeature` singleton) cannot be resolved from JSON alone. The loader will return a partially-wired `MaterialBuilder` (or a `MaterialInstance` with placeholder nulls) and the callsite calls a small `wireRuntime(lights, shadowTex, fogFeature)` helper.
- `nlohmann_json` is already linked to `snake3d_engine`, so no CMake changes are needed for the loader itself.
- The JSON files live under `Assets/Materials/` and are copied to the build dir by the existing `copy_assets` CMake target (no new copy target needed).
- Scope is **load-time only** (static config). Hot-reload (watch JSON file mtime, F-key reload) is explicitly **out of scope** for D3.

**Analogous implementation reference:** `App.cpp::loadAssets` at line 390 (manifest + `nlohmann::json` iteration → `ResourceManager::loadAsyncTexture` calls). Pattern: open file, `j >> ...`, iterate entries, drive engine API.

**Test infrastructure.** `Tests/MaterialBuilderTests.cpp` tests `MaterialBuilder` without an OpenGL context. A new `MaterialLoaderTests.cpp` can follow the same pattern — parse JSON strings in-memory, verify the resulting `MaterialBuilder` has the expected master name, feature count, and feature types.

**ShaderRegistry hot-reload precedent.** `ShaderRegistry::reloadIfChanged()` (polled on F10 → `RenderManager::reloadShaders`) shows how the engine supports non-recompilation refresh cycles. D3's static JSON loading is a simpler one-shot version of the same philosophy.

## Plan

- [x] **Step D3.1 — JSON schema design + pilot material JSON files** (no C++ changes): define `Assets/Materials/snake_tile.json`, `Assets/Materials/barrel.json`, `Assets/Materials/torch.json`. Schema:
  ```json
  {
    "master": "basicShader",
    "blending": "opaque",
    "features": [
      { "type": "lighting" },
      { "type": "shadow" },
      { "type": "albedo", "color": [0.88, 0.05, 0.05] },
      { "type": "fog" }
    ]
  }
  ```
  Feature entries with texture references use the texture manifest key (resolved at load time via `ResourceManager::getTexture`):
  ```json
  { "type": "albedo", "texture": "torch.png", "ambientIntensity": 1.0 },
  { "type": "normalMap", "texture": "torch_normal.png" },
  { "type": "specular",  "texture": "gamefield_specular.jpg", "shininess": 32.0 }
  ```
  Features requiring runtime wiring (`lighting`, `shadow`, `fog`) carry only their type name — no texture or pointer fields. `blending` is optional (defaults to `opaque`). Accepted blending values: `"opaque"`, `"translucent"`, `"alphaAdditive"`.

- [x] **Step D3.2 — `MaterialLoader` class** (engine layer — new files):
  Create `Resource/MaterialLoader.h` and `Resource/MaterialLoader.cpp`. Public API:
  ```cpp
  namespace Resource {
    struct MaterialSpec {
      Material::MaterialBuilder builder;  // pre-populated with static features
      bool hasLighting{false};
      bool hasShadow{false};
      bool hasFog{false};
      Blending::Mode blending{Blending::Opaque};
    };
    MaterialSpec loadFromFile(const std::string& path, const Manager::ResourceManager& rm);
    MaterialSpec loadFromJson(const nlohmann::json& j, const Manager::ResourceManager& rm);
  }
  ```
  `loadFromFile` opens the file and delegates to `loadFromJson`. `loadFromJson` iterates `j["features"]`, maps each `"type"` string to the corresponding feature constructor, populates static data (color, textures via `rm.getTexture(key)`, scalars), sets `hasLighting/hasShadow/hasFog` flags for runtime-wired features. Unknown `"type"` values emit `std::cerr` warning and are skipped.
  Feature type → class mapping (exhaustive for known types; unlisted types skipped):
  - `"albedo"` → `Feature::AlbedoFeature` (params: `texture?`, `color?` as `[r,g,b]`, `alpha?`, `ambientIntensity?`)
  - `"normalMap"` → `Feature::NormalMapFeature` (params: `texture`)
  - `"specular"` → `Feature::SpecularFeature` (params: `texture`, `shininess?`)
  - `"pbr"` → `Feature::PbrFeature` (params: `metalness`, `roughness`, `aoMap?`)
  - `"fog"` → sets `hasFog=true`, no object added yet (wired by callsite)
  - `"lighting"` → sets `hasLighting=true`, no object added yet
  - `"shadow"` → sets `hasShadow=true`, no object added yet
  - `"uvTransform"` → `Feature::UvTransformFeature` (params: `scale?` as `[u,v]`, `offset?` as `[u,v]`)
  - `"bones"` → `Feature::BonesFeature` (params: `useBones?` bool)
  - `"ibl"` → `Feature::IblFeature` (params: `texture`)

## Open questions

- **Barrel lazy-texture pattern**: `BarrelNode3D::update` polls `albedoFeature->getAlbedo() == nullptr` to know when the async model's embedded texture is ready, then calls `setAlbedo(tex)`. After JSON migration `albedoFeature` starts as a `nullptr`-albedo feature (same as today), so this still works — but the loader must create an `AlbedoFeature(nullptr)` when `texture` key is absent (or texture not yet loaded). Confirm this is correct behavior before D3.6.
- **Feature order matters for shader permutation hash**: `MaterialBuilder` passes features to `ShaderRegistry::makeKey` in insertion order. The JSON array order must match the original C++ insertion order for the same shader permutation to be cache-hit. This is a correctness requirement — document it in the JSON schema.
- **`featuresView()` returns a `const vector&`**: extracting member pointers for barrel's lazy pattern requires read-only iteration + `dynamic_pointer_cast`. The `spec.builder` is mutable before `build()`, so features added via `with(...)` can still be appended after extraction. Confirm this flow compiles cleanly.
- **Hot-reload (out of scope for D3, but design note)**: if hot-reload is added in D4, `MaterialLoader::loadFromFile` would need to watch the JSON mtime alongside the shader sources in `ShaderRegistry::reloadIfChanged`. Design the loader interface so it can be called repeatedly without side effects.
- **`copy_assets` copies `Assets/` recursively**: a new `Assets/Materials/` subdirectory will be picked up automatically. Confirm the copy target at CMakeLists.txt line 44 uses `-E copy_directory` (it does), so no CMake changes needed for the asset copy.
